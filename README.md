# GT4Hooks

Code hooks for the Gran Turismo 4 family of PlayStation 2 titles, injected with
[PS2 Plugin Injector](https://github.com/ermaccer/ps2plugininjector).

These games all run the same Polyphony Digital engine, so the repository is
organized around that: one shared engine layer, and a thin layer per game.

## Features

### Gran Turismo 4 Online
* **HostFS** — loose file loading.
* **`HOutput`** — the game's own debug output class, stripped in release builds,
  is reimplemented so its messages print. This is distinct from `LOG()`: it
  un-stubs something the *game* calls.
* **`CameraSys::CameraOnBoard::GetCameraMountIndex`** — three extra cameras.
* **`mStorageMC::getFileSize`** — implemented, so adhoc scripts can save and
  load from the memory card properly.
* **`mCarGarage::getPerformanceIndex`** — a new adhoc method returning a car's
  performance index. Also a worked example of extending a built-in adhoc module.
* **`Custom MStorage data handler`** - Added support for extra data variables to be
  loaded into memory that persist across all game transitions, manipulated with adhoc,
  then saved to the memory card as an external file that holds all the variables.
  Integers, floats, and strings are supported.
```
Place these function calls at the correct spots in ..share/memorycard.ad,
and #include extraData.ad at the top: (See the templates provided at source/games/gt4o/templates/adhocScript/)
InitializeExtraData(); 		// Creates mc0:/<game save folder>/ExtraData.txt and populates each variable with the default values
LoadExtraData(); 			// Loads mc0:/<game save folder>/ExtraData.txt
SaveExtraData(); 			// Updates all extra variables for mc0:/<game save folder>/ExtraData.txt

Call these functions in any adhoc script:
main::menu::MStorage::getStorage(1).loadVars(path)	// Loads all extra data into memory. 0 = HDD, 1 = mc0, 1 = mc1
main::menu::MStorage::getStorage(1).saveVars(path)	// Saves all extra data from memory to the file 0 = HDD, 1 = mc0, 1 = mc1
main::menu::MStorage::getExtraData(name) 			// Fetches an extraData variable from memory
main::menu::MStorage::setExtraData(name, value) 	// Sets an extraData variable in memory. Strings ≤ 255 bytes, no control characters. Anything else — array, map, nil — is refused

main::menu::MStorage::getStorage(1).setVar(path, "variable", value) 	// Fetches an extraData variable from the file instead of memory. Not really needed
main::menu::MStorage::getStorage(1).getVar(path, "variable") 		// Sets an extraData variable to the file instead of memory. Not really needed
main::menu::MStorage::getStorage(1).delVar(path, name) 				// "Deletes" an extraData variable. idk if this needs to exist. Returns 1 if removed, 0 otherwise

main::menu::MStorage::getStorage(1).read(path) 						// Fetches the whole file as a string
main::menu::MStorage::getStorage(1).write(path, contents)			// A dumb text/data inserter. Writes whatever is inside the second argument from the beginning of the file.
main::menu::MStorage::getStorage(1).ping()							// Diagnostic, should return 42. If not, something's wrong
main::menu::MStorage::getStorage(1).echoVar(value)					// Diagnostic, sends the argument through a round-trip.
```

### Tourist Trophy
* **HostFS** — loose file loading.
* **`HOutput`** — the engine's own debug output class, stubbed in release
  builds, is restored so its messages print.

### Injecting code hooks into ELFs
1. Run [GT4ElfBuilderTool](https://github.com/Nenkai/PDTools/releases/tag/elfbuilder-1.0.0): Decompress a CORE ELF (`CORE.gt4`, `CORE.tt`, etc.)
2. Run [ps2plugininjector](https://github.com/ermaccer/ps2plugininjector): Inject a plugin ELF generated by GT4Hooks into the decompressed CORE ELF (BASE_*.ELF)
3. Move the modified ELF into the folder where game files live

### Enabling HostFS in PCSX2
1. After generating the HostFS-enabled ELF:
2. Make sure it has an `.elf` or `.ELF` extension so it can be detected by PCSX2.
3. Add the folder containing the ELF as a search directory: `Settings` → `Game List` → `+Add...`
4. Exit settings and then find the new game list entry, then right-click it → `Properties...`
5. `Summary` → `Disc Path` → `Browse` → select the ISO. Either the original, or your specific copy of it for modding purposes
6. Optional: Change the `Title` so it's easier to recognize in the game list
7. `Emulation` → Then enable `Enable Host Filesystem`.

# General Documentation

## How injection works

The injector appends a new `PT_LOAD` segment holding the plugin's `.text`, then
overwrites the **first `ei` instruction** in the executable with a
`jal INVOKER`. That instruction sits at `0x001001F8` in every build this
repository targets — Gran Turismo 4 Online and all three Tourist Trophy builds —
which is very early startup, well before the game's own subsystems come up.

The practical consequence is that a plugin's init function runs before almost
anything else, so it can patch globals the game has not read yet. Both games
rely on that.

## Naming

Games are identified by a short id, which is also their directory under
`source/games/`:

| Id | Game |
|---|---|
| `gt4o` | Gran Turismo 4 Online |
| `gt4` | Gran Turismo 4 |
| `tt` | Tourist Trophy |

# Developer Documentation, Building

Everything below is for building the hooks from source. If you only want to use
them, the two sections at the top are all you need.

Everything is C. C++ will not work — see the injector's own README.

| Variable | Default | Holds |
|---|---|---|
| `PS2SDK_HOME` | `..\ps2sdk-main` | the ps2sdk checkout, including its bundled EE toolchain |
| `WORK` | `..\GT4Hooks-work` | `bases\`, `out\`, `cache\`, `ps2plugininjector.exe` |

Both are read from the environment, so set them if your layout differs:

```
set PS2SDK_HOME=D:\ps2\ps2sdk
set WORK=D:\ps2\gt4hooks-work
```

### ps2sdk

GT4Hooks needs a ps2sdk checkout that bundles the EE toolchain — specifically
`ee/bin/mips64r5900el-ps2-elf-gcc.exe`, `ee/bin/make.exe` and
`ee/bin/vsmake.ps1`, plus the SDK tree under `ps2sdk/`.

**No changes to ps2sdk are required to build this project, and none have been
made.**

`mk/eemakefile.eeglobal` and `mk/linkfile` are GT4Hooks' own files, derived from
the ps2sdk samples.

### The injector

`build.bat` runs `ps2plugininjector.exe` from `%WORK%` as its last step, so a
source build produces the finished ELF in one go rather than leaving you to
inject by hand. Base images go in `%WORK%\bases\BASE_<BUILD>`, produced with
GT4ElfBuilderTool exactly as in the end-user steps above.

Two quirks of the injector are worth knowing before changing that step — see
[Toolchain notes](#toolchain-notes).

## Generating a code hook plugin

```
build                    list the games and their regions at source\games\
build gt4o US            build Gran Turismo 4 Online, US region
build tt US              build Tourist Trophy, US region
build clean tt US        remove Tourist Trophy US's output
```

`build` with no arguments scans `source\games\` for directories containing a
`game.mk` and prints each one with its regions

Omitting the region builds that game's `DEFAULT_REGION`.

Output lands in `%WORK%\out\<game>\<build>\`: `plugin.elf` (the plugin),
`plugin.map`, and the injected boot ELF ready for PCSX2. If no base image is
present for a build, the plugin is still produced and injection is skipped.

The plugin links against **nothing** from the SDK. Every libc and kernel call it
makes goes to the *game's* own copy through a function pointer, so the only
thing the linker needs is the linkfile. That is why `NEWLIB_NANO` and
`KERNEL_NOPATCH` are off: current ps2sdk no longer ships `libps2sdkc` or
`libkernel-nopatch`, and nothing needs them.

## Repository layout

```
mk/                     build machinery, shared and game-agnostic
  linkfile              where the plugin's sections go
  eemakefile.eeglobal   derived from the ps2sdk samples
tools/                  generic analysis and verification
  tt/                   the Tourist Trophy port, kept as a worked example
source/
  core/                 compiled into EVERY game. No address literal, no game name.
    Target.h            THE SEAM - see below
    Log.h               LOG() over the SIO port
    ps2/                PS2/MIPS hardware: Memory.c (hook primitives), Sio.c
    pdistd/             the Polyphony engine ABI: FileDevice, SceStructs, SceEnums,
                        FileError - identical across the family
    game/               pointers bound into the game's own code: IO, String,
                        FileDevice
    util/               generic string helpers
  games/                one directory per game. Peers. No default.
    gt4o/               main.c, game.mk, GameConfig.h, Targets/, plus the hooks
                        only it has: CameraSys, MStorage, MCarGarage, Adhoc
    tt/                 main.c, game.mk, GameConfig.h, Targets/
```

## The seam: how shared code reaches game addresses

Every address literal lives in exactly one place: a per-build header under
`source/games/<game>/Targets/`. Shared code reaches them through
`source/core/Target.h`, which is a handful of lines:

```c
#ifndef TARGET_HEADER
#error "TARGET_HEADER is not defined..."
#endif
#include TARGET_HEADER
```

The makefile supplies both halves:

```
-DTARGET_HEADER='"SCUS-97436.h"'  -Isource/games/gt4o/Targets
```

so nothing outside a game's own directory needs to know which game or region is
being built.

### Adding a region to an existing game

1. Resolve the addresses (see below) and write
   `source/games/<game>/Targets/<BUILD>.h`.
2. Add a `BUILD_<REGION>` / `ELF_<REGION>` / `BASE_<REGION>` trio to that
   game's `game.mk`, and list the region in `REGIONS`.
3. Drop `GT4Hooks-work\bases\BASE_<BUILD>` in place.
4. `build <game> <REGION>`.

No C changes, no header edits, nothing at the repository root.

### Adding a whole game

Create `source/games/<name>/` with `game.mk`, `main.c` and `Targets/`. The
root makefile discovers it by globbing `source/games/*/game.mk` and contains
no game name of its own, so nothing else changes.

## Where the injected code lives

The plugin has to be linked somewhere the game will never read or write. This is
the single hardest thing to get right when adding a game, and the two games
solve it differently because the games differ — see Part 2.

The shared constraint: shortly after startup the game hands a generic pool
allocator everything from a link-time-constant base up to the top of RAM, and
zero-fills it. Code inside that range can be handed out as an allocation, so it
must sit below the pool base, or the pool base must be moved.

`tools/tt/find_free_space.py` will scan for unreferenced gaps, but treat its output
with suspicion: a large static array only ever has its *base* address
materialised in code, so the interior of a perfectly live buffer looks exactly
like free space to a cross-reference scan.

## Debug output

**Do not call the game's `printf` from a hook.** It works from the plugin's init
function — the startup banner appears — but the same call from inside a file
device hook produces nothing, even though the hooks demonstrably run and the
compiled call sequence is identical: both load the pointer from the same global
and `jalr` through it. Something about the game's stdio state after startup
swallows it.
(Issue specifically encountered with Tourist Trophy, which is why this was changed)

Use `LOG()` from `core/Log.h`. It formats with the game's `sprintf`, which is
known good, and emits the result over the EE SIO transmit register at
`0x1000F180`. PCSX2 collects those writes into its console and real hardware
sends them out the SIO port; neither depends on anything the game initializes.

`LOG` compiles to nothing when `HOSTFS_PRINT` is 0.

## Host Filesystem

The HostFS hook redirects the game's volume reader at the loose files in
`HOST_DIR` (default `VOL_extract`), so assets can be edited without rebuilding
the VOL.

Sound and movie files are deliberately **not** redirected. They are handed to
`PDISTR.IRX` over RPC (ids `MPG1`, `MPG2`, `PBGM`, `STRP`) and read straight
into IOP RAM, which an EE-side host file descriptor cannot satisfy. The
extensions concerned — `ins`, `ads`, `sqt`, `es`, `pss` — are the same in every
game in the family. The *path prefixes* are not; see Part 2.

## Resolving addresses for a new game or region

Every game in this family is built from the same source, so individual functions
compile to identical machine code and differ only in placement. That makes a new
target largely mechanical, and it is how all three Tourist Trophy builds were
resolved from the known Gran Turismo 4 Online addresses.

The tools implement it. `tools/` holds the ones that work on any game;
`tools/tt/` holds the Tourist Trophy run, kept as the worked example of porting
a game — along with the JSON its stages produced.

| `tools/` | Does |
|---|---|
| `ttanalyze.py` | MIPS R5900 analysis: ELF loading, disassembly, xrefs, fingerprints. Every other tool builds on this |
| `check_game.py` | re-verifies any game's generated headers against the real executables |
| `clamp_bss.py` | post-injection `.bss` memsz clamp; run by `build.bat` |
| `gen_vsproject.py` | regenerates the Visual Studio project from the tree |

| `tools/tt/` | Does |
|---|---|
| `resolve_tt.py` | fingerprint match — operand-stripped mnemonic sequences |
| `resolve_stage2.py` | what fingerprints cannot separate: leaf helpers and globals, from call-graph position |
| `resolve_printf.py` | the printf-family stubs, which are operand-identical to each other |
| `resolve_houtput.py` | HOutput: a pointer holding a one-instruction stub, plus two identical functions |
| `resolve_injection.py` | locates the pool setup and its memset call |
| `consolidate.py` | merges the stages and *requires* them to agree where they overlap |
| `make_injection.py` | injection parameters, with the safety checks |
| `gen_headers.py` | emits the per-build `Targets/` headers |
| `find_free_space.py` | scans for unreferenced gaps — read the caveat above before trusting it |

Porting another game means writing the equivalent of `tools/tt/` for it. The
Tourist Trophy set is deliberately kept intact so there is a complete example to
follow rather than a description of one.

The method, briefly:

1. Build a candidate inventory: every `jal` target **union** every word in the
   image that points into `.text`. The union matters — virtual functions are
   only ever reached through vtables, so they are never `jal` targets.
2. Fingerprint each candidate by its mnemonic sequence with all operands
   stripped. Same source, same fingerprint, regardless of address.
3. Look up each known address's fingerprint in the new image.
4. Verify by *delta consistency*: functions from one translation unit relocate
   as a block, so a correct mapping shows one constant delta across the whole
   unit. A match that breaks the pattern is wrong.

For Tourist Trophy the deltas came out as:

| Region | file layer | sce layer | vtable slots |
|---|---|---|---|
| US | +0x1A670 | −0xDF9C8 | −0xFF320 |
| EU | −0x36148 | −0xDC288 | −0xFFB88 |
| JP | +0x14670 | −0xE8808 | −0x10CBB8 |

## Toolchain notes

* **GCC 14** promotes several pointer diagnostics to errors that older
  toolchains only warned about. The casts on `readStat` vtable
  calls and on `HOOK_FUNC_ADDR` arguments exist for that reason.
* **`ps2plugininjector` returns a non-zero exit code even when it succeeds**, so
  `build.bat` checks for the output file rather than trusting `errorlevel`.
* Building the injector with current MSVC needs `#include <string>` added to its
  `Patterns.h`; older compilers pulled that in transitively.

# Game Specifics

## Gran Turismo 4 Online

Target: `SCUS_974.36`

### Where its code lives

Linked at `0x68A480`, over the static globals of the Omron wnn/fep Japanese IME.
Gran Turismo 4 Online links that code but never calls it — `LoadFep` at
`0x1058D0` has no cross-references at all, so nothing below it ever runs — which
leaves `0x68A480..0x69A790` (about 64 KB) reliably dead.

That is comfortably below the pool base at `0x8D0FB0`, so the pool's zero-fill
cannot reach it. The clearing call is NOPed anyway as belt-and-braces
(`GLOBAL_MEMSET_OFFSET`).

### Streamed files

`IsStreamedFile()` excludes the `carsound/` prefix and the family-wide extension
set. Gran Turismo 4 selects its engine-sound folder from a two-entry table
`{ "motosound", "carsound" }` indexed by a vehicle-class predicate — but that
predicate is a stub that always returns zero, so only `carsound/` is ever
reachable here.

## Tourist Trophy

Targets: US `SCUS_975.02`, EU `SCES_533.72`, JP `SCPS_151.05`.

### Where its code lives

Tourist Trophy does **not** ship the wnn/fep code — `InitWnn`, `InitFep` and
`LoadFep` are absent from all three retail builds — so the Gran Turismo 4 trick
has no equivalent here, and there is no comparable dead region to borrow.

Instead it links *at* the generic pool's base and raises that base past itself in `init()`, before the pool is
ever built:

| Region | Pool base (shipped) | Plugin linked at | Reserved | Pool then starts |
|---|---|---|---|---|
| US | `0x7A69CC` | `0x7A6A00` | `0x20000` | `0x7C6A00` |
| EU | `0x7AA7FC` | `0x7AA800` | `0x20000` | `0x7CA800` |
| JP | `0x79831C` | `0x798380` | `0x20000` | `0x7B8380` |

The link base is the pool base rounded up to 128 to match the linkfile's
alignment. `init()` also raises newlib's `sbrk` break pointer, which ships
holding the same address — `sbrk` is dead code in these builds, but it costs one
store to leave nothing pointing into the reserved block.

Unlike Gran Turismo 4, the memset is **not** NOPed. The raised base already
moves the clear above the plugin, so suppressing it would only rob the game of
its zeroed pool.

`crt0` clears `.bss` up to `_end`, and `_end` *is* the pool base, so the plugin
sits just above the last byte `crt0` touches.

### The `.bss` memsz tail

Tourist Trophy's second `PT_LOAD` declares a `p_memsz` running far past
`p_filesz`, and the plugin's link address falls inside that declared tail.
Whether that matters depends on when a loader zero-fills segment tails, so
`build.bat` runs `tools/clamp_bss.py` after injection to clamp that segment's
`p_memsz` down to `p_filesz`. Safe, because `crt0` clears `.bss` itself.

### Streamed files

Tourist Trophy needs **both** `motosound/` and `carsound/` excluded, where
Gran Turismo 4 needs only the latter.

Both games build the engine-sound folder from the same two-entry table indexed
by a vehicle-class predicate. In Gran Turismo 4 that predicate is a stub. In
Tourist Trophy it is real: it reads the vehicle's class and returns true for the
two-wheel class, so bikes load engine sounds from `motosound/`. This hints that the engine was built with the intention to include both cars AND bikes in future games.

The sound root also changed (`/sound_gt` → `/sound_tt`), but that must **not**
be added: everything under it that actually streams is already covered by the
extension tests, and a `sound_tt/` prefix would wrongly pin non-streamed files
there to the disc.

### A note on the Japanese executable

`SCPS-15105_CORE.TT` does not pass `GT4ElfBuilderTool`'s optional RSA
authentication, while the US and EU images do. Decompression is unaffected and
the resulting ELF is structurally sound.
